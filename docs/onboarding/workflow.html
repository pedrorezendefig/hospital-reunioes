01

A ideia em um minuto

Três princípios sustentam tudo. Se você entender estes, o resto é seguir o caminho.

A

A issue é a memória

Nada de pastas de planejamento pesadas. Cada pedaço de trabalho vira uma issue no GitHub: ela guarda o que fazer, os critérios de aceite e o progresso. Fechou a sessão? O contexto está na issue, não na sua cabeça.

antes: docs/planejamento · agora: GitHub Issues
B

Cada trabalho é uma fatia fina

Em vez de “fazer todo o banco, depois toda a tela”, cada issue é uma fatia vertical: atravessa banco → API → tela → teste e já funciona sozinha. Pequena, testável, demonstrável.

tracer bullet · fatia vertical
C

Várias sessões ao mesmo tempo

Como as fatias são independentes, você abre vários terminais do Claude e cada um pega uma issue diferente. Trabalho de muita gente (ou muitos agentes) acontece em paralelo, sem pisar um no outro.

N terminais · 1 issue cada
02

O caminho, do início ao ar

Sete comandos, em ordem. Você não precisa decorar o que cada um faz por dentro — só a sequência.

01

Afie a ideia /grill-with-docs

Você conversa, e o Claude questiona seu plano contra o domínio — o que é Reunião, Ata, Pendência? Termos importantes ficam anotados no CONTEXT.md.

→ vocabulário afiado · CONTEXT.md / ADR atualizados
02

Vire um PRD /to-prd

O Claude transforma a conversa num documento curto (problema, solução, histórias de usuário) e publica como uma issue no GitHub, com a etiqueta ready-for-agent.

→ 1 issue “PRD” no GitHub
03

Quebre em fatias /to-issues

Aquela issue grande vira várias issues pequenas e independentes — cada uma uma fatia vertical, com critérios de aceite e o campo “Bloqueada por”.

→ N issues prontas pra pegar
04

Pegue uma fatia /pegar-issue

Numa sessão do Claude, você pega uma issue livre. Ela vira sua (o “claim”), some da fila dos outros e ganha uma branch. Sem argumento, ela lista o que está disponível.

→ issue sua · branch criada
05

Teste primeiro /tdd

Cada critério de aceite vira um teste. Vermelho (falha) → verde (passa) → arruma. O código nasce coberto e a issue vira a especificação executável.

→ código + testes verdes
06

Suba com revisão /ship

Abre o Pull Request, roda os portões (revisão de código, segurança quando preciso, e o CI), aprova e faz o merge. O Closes #N fecha a issue sozinho.

→ PR mesclado · issue fechada
07

Vai pro ar /deploy

O Coolify publica, confere a saúde do sistema (/api/health) e reverte sozinho se algo falhar. O CHANGELOG e o mapa da app se atualizam automaticamente.

→ produção saudável · versão visível no rodapé
03

Por que “fatia vertical”?

A diferença entre travar e fluir está em como você corta o trabalho.

Tela (frontend)
API (endpoints)
Regras / serviços
Banco (schema)
Testes
cada fatia (faixa colorida) corta TODAS as camadas → entrega algo que funciona

Uma fatia vertical corta todas as camadas de uma vez e entrega um comportamento completo, por menor que seja. “O facilitador vê quem já assinou a ata” já envolve banco, API, tela e teste — mas é pequena.

O contrário é a fatia horizontal: “fazer todo o banco” numa semana, “toda a API” na outra. Ninguém consegue testar nada até o fim, e duas pessoas não conseguem trabalhar sem se atrapalhar.

Por isso o /to-issues prefere muitas fatias finas a poucas grossas: cada uma é demonstrável, revisável e — o ponto principal — paralelizável.

Trabalhando em paralelo

Três terminais do Claude, três issues diferentes, zero colisão. Cada um no seu worktree (uma cópia isolada da pasta, mesmo histórico Git).

✓ claim #42

worktree ../hospital-issue-42
▶ /tdd rodando…
terminal 2
$ /pegar-issue 43

worktree ../hospital-issue-43

terminal 3
$ /pegar-issue 44
✓ claim #44

worktree ../hospital-issue-44

O “claim”: como ninguém pega a mesma issue

Quando você roda /pegar-issue N, isto acontece em segundos — e é o que evita duas sessões no mesmo trabalho.

1

Vê a fila

Lista só issues ready-for-agent sem dono e sem bloqueio. Você escolhe uma.

2

Trava (claim)

Tira a etiqueta ready-for-agent, põe in-progress e se marca como dono. A issue some da fila dos outros.

3

Confere

Relê os donos. Se por acaso dois pegaram junto, um abre mão e pega a próxima. Sem briga.

4

Isola

Cria um worktree e a branch da issue. Cada sessão mexe na sua cópia — sem conflito de arquivos.

★

Regra de ouro: uma issue por sessão, um worktree por issue. É isso que deixa o paralelo seguro — sem Docker, sem mágica, só isolamento nativo do Git.

06

Bloqueantes: a ordem certa

Nem tudo pode começar ao mesmo tempo. Quando uma fatia precisa de outra, ela diz “Bloqueada por #X”. Aperte Simular e veja a ordem do nosso exemplo se desenrolar.

bloqueada liberada (pode pegar) em progresso concluída
Onda 1 — a base (sozinha)
#42liberada
Endpoint de status dos signatários
bloqueada por: — (pode começar já)
Onda 2 — em paralelo (depois de #42)
#43bloqueada
Card listando quem assinou
bloqueada por: #42
#44bloqueada
Botão “lembrar” quem falta
bloqueada por: #42
Onda 3 — depois do card
#45bloqueada
Atualização automática (30s)
bloqueada por: #43
→

Como lidar na prática: só pegue issues liberadas (sem bloqueio aberto). Quando você fecha uma base, o Claude tira a etiqueta blocked das filhas e elas caem na fila. Trabalho que não depende de nada é o mais valioso — ataque essas fatias primeiro e o paralelo rende ao máximo.

07

As etiquetas (estados da issue)

São as cores do quadro. Você raramente mexe nelas à mão — as skills cuidam — mas é bom reconhecer.

ready-for-agent

Especificada por completo. Está na fila, qualquer sessão pode pegar.

in-progress

Alguém deu o claim e está trabalhando. Saiu da fila.

blocked

Tem uma dependência aberta (“Bloqueada por #X”). Fora do pool paralelo até a base fechar.

ready-for-human

Precisa de decisão ou implementação humana (HITL). Não é pra agente autônomo.

needs-info

Falta informação pra começar. Aguardando quem abriu responder.

needs-triage

Issue nova, ainda não avaliada. Passa pelo /triage antes de virar trabalho.

i

AFK × HITL: uma fatia AFK um agente faz sozinho, do começo ao fim. Uma HITL precisa de você (uma decisão de design, uma escolha de arquitetura). Só as AFK liberadas entram no paralelo automático.

08

Os portões antes de subir

Enxuto, mas com rede de segurança. O /ship só faz o merge com tudo verde.

sempre

Revisão de código

O Claude relê o diff procurando bugs, casos de borda e clareza. /code-review.

roda em todo PR
condicional

Revisão de segurança

Entra quando o diff mexe em login, dados sensíveis, migrations ou webhooks. /security-review.

só em área sensível
automático

CI (testes)

O GitHub Actions roda lint + testes do backend e do frontend, e o build. Vermelho trava o merge.
